# CLAUDE.md - AI Assistant Guide for dAImond-lang

## Project Overview

dAImond is a systems programming language designed to be the fastest compiled language, the most AI-generatable language, self-compiling, memory-safe without garbage collection (region-based with full inference), and fully Turing-complete at compile time.

The repository contains one compiler, written in dAImond, in `stage5/`. The directory's name is historical: it was the fifth compiler stage, and the earlier ones are deleted (see History). It compiles itself, and what it builds contains no C: the runtime of every program (`stage5/runtime/*.dm`) and the compiler's bridge to LLVM (`llvm_bridge.dm`) are dAImond code. A new machine gets its first compiler from a seed, `seed/daimond.bc` (the compiler as LLVM bitcode), which `bootstrap.sh` turns into a compiler with LLVM's `llc` and `ld.lld`. Building needs no C compiler and no other language's toolchain. It needs LLVM and the C library, which the runtime calls.

## Compiler Pipeline

```
Source (.dm) -> Lexer -> Tokens -> Parser -> AST -> Validation -> Check (names, types, effects) -> IR Gen -> dAImond IR -> LLVM Gen (via the LLVM bridge) -> LLVM IR -> LLVM -> Object -> ld.lld -> Native Binary
```

## Build Commands

The compiler is built from the seed by `bootstrap.sh`, or by a dAImond compiler you already have. It needs x86-64 Linux with glibc, LLVM 19 or newer with `lld` (LLVM 19 and LLVM 23 have been run), and the C library's development files (`Scrt1.o`, `crti.o`, `crtn.o`, `libc.so`). It needs no C compiler, to build programs or to build itself.

```bash
# Build the compiler from the seed (about six minutes, 1.4 GB of memory)
sh bootstrap.sh                 # -> build/daimond
sh bootstrap.sh -o /tmp/daimond

# After changing the compiler so that an older compiler can no longer build it: write the seed again
# (with LLVM 19, so that the seed stays readable by LLVM 19 and newer)
build/daimond run stage5/gen_bootstrap.dm && LLVM_BIN=/usr/lib/llvm-19/bin sh bootstrap.sh --update-seed

# Compile a dAImond program to a native binary
build/daimond <file.dm> -o output

# Compile with optimization
build/daimond <file.dm> -o output -O2

# Emit dAImond IR (debugging)
build/daimond <file.dm> --emit-ir

# Emit LLVM IR (debugging)
build/daimond <file.dm> --emit-llvm

# Emit LLVM bitcode, as it goes to code generation (<output>.bc)
build/daimond <file.dm> --emit-bitcode -o output

# Build with debug info, for gdb and lldb
build/daimond <file.dm> -g -o output

# Compile and run; the arguments after -- go to the program, and the exit code is the program's
build/daimond run <file.dm> -- arg1 arg2

# Report the file's errors without building anything
build/daimond check <file.dm>

# Indent the file by its braces, in place (or into -o <file>)
build/daimond fmt <file.dm>

# Run each fn test_*() of the file in its own process and report PASS or FAIL
build/daimond test <file.dm>

# List the file's declarations, one per line, for editors
build/daimond symbols <file.dm>

# Build the language server; it runs the `daimond` next to it (or --compiler <path>, or $DAIMOND)
build/daimond lsp/main.dm -o build/daimond-lsp

# check and symbols (and a plain compilation) can read the program from standard input;
# the file name is then only its name, and where its imports are looked for
build/daimond check <file.dm> --stdin < unsaved.dm

# Regenerate main.dm and prelude.dm from the modules (also after editing runtime/*.dm or llvm_bridge.dm)
build/daimond run stage5/gen_bootstrap.dm
build/daimond run stage5/gen_bootstrap.dm -- --check    # writes nothing; exits with 1 when they are stale

# Compile the compiler with a compiler you already have (--link-llvm adds llvm_bridge.dm and links libLLVM)
cd stage5 && ../build/daimond main.dm -o /tmp/daimond_new --link-llvm

# Run the integration suite against a compiler (565 cases, about a minute)
build/daimond tests/harness.dm -o build/harness
build/harness build/daimond                              # every case in tests/cases
build/harness build/daimond tests/cases 17_lists/        # only the cases whose "suite/name" contains the text
```

## Testing Strategy

1. **The suite** (`build/harness <compiler>`): `tests/harness.dm`, a dAImond program, compiles every case in `tests/cases/` with the compiler it is given, runs the program and compares stdout, the exit code and, where the case has an `X.stderr`, stderr. A case with `X.errors` must fail to compile with each line of that file in the compiler's output. A case that is a directory `X/` has its program in `X/main.dm`, next to the files it imports. The harness starts the compiler and each program itself (`run_command_io`), with no shell. A case with `X.cmd` runs that shell command (`sh -c`, the suite's only use of a shell) instead of compiling and running the program, and its output and exit code are compared the same way; in it `{compiler}`, `{source}` and `{work}` stand for the compiler, the case's program and an empty directory (`81_commands` tests `run`, `check`, `fmt` and `test` this way). Currently 565 pass, 0 fail. The suite began as the cases of the Zig compiler's test runner. It also holds the 19 memory-safety probes (`74_memory_safety_probes`), and programs that were once loose files in `tests/`, with the README's examples (`86_programs`). To add a case, add `X.dm` and `X.stdout` (or `X.errors`) to a suite directory.

2. **dAImond test framework** (`daimond test <file.dm>`): runs each `test_*` function of the file in its own process, so a panic ends only that test. Tests use `assert(cond)` and `assert_eq(actual, expected)`.

**After changing the compiler, run `build/harness` on the new compiler, and `sh bootstrap.sh` to check that it still reproduces itself.** The suite is the record of what the compiler does: add a case for what you change.

## Code Conventions

### dAImond Style (language source files)

- **Comments**: `--` for line comments (double dash, not `//`)
- **Module declaration**: Every file starts with `module <name>`
- **Immutability by default**: `let x = 42`, `let mut x = 0` for mutable
- **Functions**: `fn name(params) -> RetType { body }` or `fn name(params) -> RetType = expr`
- **Effects**: Declared with `with [Effect1, Effect2]` on function signatures
- **Regions**: `region name { ... }` for scoped memory management
- **Pattern matching**: `match value { Pattern => expr, ... }`
- **Error propagation**: `?` operator on Result types
- **Pipe operator**: `|>` for function chaining
- **File extension**: `.dm`

### The Compiler's Source

- **Integer kind tags**: an AST or IR node is one struct with a `kind` and the fields of every kind (`fn EXPR_FUNCTION_CALL() -> int { return 40 }`). Check the kind before reading a `Box` field: dereferencing a null `Box` panics.
- **Expression ids**: `expr_new` gives every expression a number of its own (`Expr.id`), and a copy keeps the number of the original. The checker records each expression's type at its id, and IR generation reads it there. An expression made during IR generation has an id the checker never saw, and so no checked type.
- **State is passed and returned**: the generator structs (`IRGenerator`, `LLVMGenerator`, `Parser`) are values. A function takes one, changes its copy and returns it: `g = ir_type_error(g, ...)`, `let result = generate_expr(g, b, e)` then `g = result.gen`. A change to a copy that is not returned is lost.
- **Errors**: a syntax error is `p_error(pp, "expected ... but got ...")`; a type error is `c = ck_error(c, message, line)` in the checker; an error found during IR generation is `g = ir_type_error(g, message, line)`, and the compilation fails after the function is generated.
- **Section headers**: `-- ====...` comment bars separate the sections of a file.
- **Types as strings**: a type is its name, in source form (`List[int]`) or IR form (`i64`, `string`, `ptr`); `map_type_name` goes from the first to the second.

## Key Architecture Decisions

1. **One compiler, built from a seed**: the compiler is written in dAImond and has no other implementation. `seed/daimond.bc` is an earlier build of it as LLVM bitcode; `bootstrap.sh` turns it into a compiler with `llc` and `ld.lld`, compiles the source with it, and repeats until two generations are the same file.

2. **LLVM as the backend**: the compiler generates its own SSA IR, then LLVM IR through LLVM's C API, and LLVM writes the object file. `ld.lld` links it with the C library's start-up objects.

3. **No C**: the runtime is dAImond code that calls libc through `extern fn`, and the compiler calls LLVM's C API the same way. No C source is compiled when the compiler or a program is built.

4. **No garbage collector**: memory is meant to be managed by regions. Today the compiler enforces that a region's values do not leave it, and the runtime frees nothing: strings and what a region allocates stay allocated until the program ends.

5. **One target**: x86-64 Linux with glibc. The OS constants and struct layouts in `runtime/*.dm` and the seed are for that target.

## Common Development Tasks

### Changing the compiler

1. Edit the split modules in `stage5/` (never `main.dm`), then run `build/daimond run stage5/gen_bootstrap.dm`
2. Build it: `sh bootstrap.sh` (from the seed), or with a compiler you already have: `cd stage5 && <compiler> main.dm --link-llvm -o /tmp/daimond_new`
3. Run the suite: `build/harness /tmp/daimond_new` (build the harness once with `build/daimond tests/harness.dm -o build/harness`); add a case to `tests/cases/` for what you changed
4. The compiler's own source may only use what the seed's compiler can compile. To use a new language feature in the compiler: add the feature, write the seed again (`sh bootstrap.sh --update-seed`), commit both, and only then use it
5. Before committing, `sh bootstrap.sh` must reach a fixed point, and `main.dm` and `prelude.dm` must be what `gen_bootstrap.dm` writes (`-- --check` says whether they are)

### Adding a language feature

1. Add token kinds in `token.dm` and `lexer.dm` if new syntax is needed
2. Add the AST fields in `ast.dm` (and, if the node has child expressions, to `names_in_expr`/`names_in_stmts` there, which lambda captures walk the tree with, and to `sc_scan_expr`/`sc_expr` or `sc_scan_stmts`/`sc_stmts`, which rename shadowed variables; a node that declares a variable must declare it there too) and the parsing in `parser.dm`
3. Give it a type in `check.dm`: a new expression in `ck_expr_of_kind`, a new statement in `ck_stmt`. What the checker does not know has the type `""` and is not checked. `ck_expr` records the type for IR generation; an expression whose value comes from its parts, as an `if`'s does, also needs a case in `ck_settle` and `ck_needs_value`
4. Generate IR for it in `ir_gen_expr.dm`, `ir_gen_stmt.dm` or `ir_gen_decl.dm`; a new IR instruction also needs `ir.dm` and `llvm_gen.dm`
5. Report misuse with `ck_error` or `ir_type_error`, and add an `X.errors` case for each message
6. Add cases to `tests/cases/`, and the keyword or builtin to `lsp/tables.dm`

### Adding a builtin function

1. In `ir_gen.dm`: its runtime name in `map_builtin_name` (`dm_X`), its name in `is_builtin_fn` and its result in `builtin_return_type`
2. In `ir_gen_decl.dm`: `declare_extern*` with its parameter and result types
3. In a `runtime/*.dm` file: the function `rt_X` with the same signature (an `int`, the address, where `dm_X` is declared with a pointer). A new runtime file also needs a line in `gen_bootstrap.dm`
4. In `ir_gen.dm`: the effect it needs, in `builtin_required_effect`, if it has one; and in `check.dm`: its parameter types, in `ck_builtin_params` (a builtin that is not listed there has its arguments checked by code generation alone)
5. In `lsp/tables.dm`: its signature and description. `tests/cases/83_language_server/completion_and_signatures.stdout` lists every builtin and needs the new one
6. A case in `tests/cases/`, and a row in the builtins reference below

### Adding a compiler diagnostic

1. Report it where it is found: `p_error` in the parser, `ck_error(c, message, line)` in the checker (what is wrong with names and types belongs there), `ir_type_error(g, message, line)` in IR generation, `lg_error` in LLVM generation
2. Add a case `X.dm` with `X.errors`, which holds each line the compiler must print

## Current Status

### Implemented

**Language features**: generics (monomorphized functions with inferred type arguments and trait bounds, generic structs with explicit ones, generic enums whose type arguments come from the values or from the place), lambdas (one that captures variables is called by the name `let` gave it), traits (static dispatch and `dyn Trait`), enums with payloads, Option/Result with `?` propagation, pattern matching, async/await, SIMD vectors (f32x4/f32x8/f64x2/f64x4/i32x4/i32x8/i64x2/i64x4), effects (builtin and user-defined), regions, comptime evaluation, operator overloading, bitwise operators (`&`, `|`, `^`, `<<`, `>>`, `~`), string interpolation, FFI/extern with C-width types and variadic functions, all numeric types (i8-i64, u8-u64, f32, f64) with `as` casts, pipeline operator `|>`, threads and mutexes, TCP sockets

**Data structures**: List[T], Map[K,V], Box[T], for-in iteration

**Type checking** (`check.dm`): undefined variables and types; `*` on what is no `Box`; an assignment to what is no place; the types of `let` values, assignments, arguments, return values, struct fields, list elements and variant values; operators and conditions; assignment to what is not `mut`, and calls that change it (`xs.push(1)`, a `mut self` method, a `mut` parameter); unknown fields and methods, of lists and strings too; undefined functions and the number of a call's arguments; the arguments of builtin functions and of functions held in fields; whether two function types agree; the effects a function declares, for the functions, methods and builtins it calls or names; `await` and calls of async functions; functions that can end without returning; matches that leave a variant out; an `if`, a `match` or a block that is used as a value and has a branch that gives none

**Tooling**: the CLI (compile, `run`, `check`, `fmt`, `test`, `symbols`), debug info (`-g`), and the language server in dAImond (`lsp/`)

**Runtime safety**: integer overflow, division by zero, shift amounts, list bounds, narrowing casts, null `Box` dereference

**Standard library** (`stdlib/`): io, math, collections, string, os, fs, net, thread, test. `import std.X` with no `std/X.dm` next to the importing file is `X.dm` in the library: the directory `$DAIMOND_STDLIB`, else `stdlib/` beside the compiler's directory, else `stdlib/` in the compiler's directory, else `stdlib/` in the current directory (`stdlib_file` in `main_split.dm`)

**The compiler**: 565/565 cases (the 19 memory-safety probes among them), run by a harness written in dAImond. `bootstrap.sh` builds it from the seed and checks that it reproduces itself; with LLVM 19 and with LLVM 23.

### Not Yet Implemented
- In the type checker: it reports a mismatch only when it knows both types. What depends on the type arguments of a generic function is reported for each instance the program uses (see Instances below), and so not at all for a generic function that is never called
- IR generation takes from the checker only what it cannot find itself (see the Type checker note under Design Decisions). It still finds the types of numbers itself, except the one an `if` or a `match` gives. The functions the compiler writes itself (`eq$...` for `==`, `contains$...`) are not checked: their types come from the expressions' parts
- Dynamic dispatch. A `dyn Trait` variable is the struct it is declared with, and its methods are called directly; assigning to it again is a compile error. A `dyn Trait` parameter is compiled for the last type that implements the trait, and a call that passes another fails to compile
- Closure values. A lambda that captures variables can only be bound with `let` and called by that name, because its captures are extra parameters that such a call passes; using it as a value is a compile error (`captured_lambda_error` in `ir_gen_expr.dm`)
- Effects of a call through a function value are those of the function, checked where it is named (`each(store, x)` uses `store`), not where the value is called
- Freeing memory: strings are never freed, and `mem_mark`/`mem_sweep` (regions) free nothing
- Targets other than x86-64 Linux with glibc
- In debug info: one scope for all of a function's variables, no bindings of `match` arms or captured variables, and no fields for `Result` and `Option`
- A package manager (the Zig compiler had one; it was not ported)

## Language Builtins Reference

These built-in functions are available in every dAImond program. The compiler recognizes them by name (`is_builtin_fn` in `ir_gen.dm`).

### I/O Functions
| Function | Signature | Description |
|----------|-----------|-------------|
| `print(s)` | `string -> void` | Print to stdout (no newline) |
| `println(s)` | `string -> void` | Print to stdout with newline |
| `eprint(s)` | `string -> void` | Print to stderr |
| `eprintln(s)` | `string -> void` | Print to stderr with newline |
| `panic(s)` | `string -> void` | Print `PANIC: <s>` to stderr and exit with code 1 |
| `exit(code)` | `int -> void` | Exit with code |
| `flush()` | `-> void` | Write out what stdout still holds |

### Terminal and Time
| Function | Signature | Description |
|----------|-----------|-------------|
| `chr(n)` | `int -> string` | One-byte string whose byte is `n` (its low 8 bits) |
| `read_key()` | `-> int` | Next byte of stdin, waiting for it (-1 at the end of input) |
| `read_key_nb()` | `-> int` | Next byte of stdin without waiting (-1 when none is waiting) |
| `term_width()` | `-> int` | Terminal width in columns (80 when stdout is not a terminal) |

| `sleep_ms(ms)` | `int -> void` | Wait for `ms` milliseconds |

### String Operators
- `+` concatenates strings: `"hello" + " " + "world"`
- `==` compares strings by value (uses `dm_string_eq`)
- `>=`, `<=`, `>`, `<` compare strings lexicographically (uses `dm_string_cmp`)

### Bitwise Operators
- `a & b`, `a | b`, `a ^ b` take two integers, which meet at one type as in arithmetic, or two bools; `a << n` and `a >> n` take integers; `~a` takes an integer
- They bind tighter than the comparisons and looser than `+` and `-`: `a & mask == 0` compares `a & mask`. Among them `|` binds loosest, then `^`, then `&`, then the shifts (`infix_prec` in `parser.dm`)
- `>>` shifts zeros into an unsigned integer and the sign into a signed one. A shift by the type's width or more, or by a negative amount, panics with `shift amount out of range` (in a compile-time expression it is a compile error). `<<` drops the bits that leave the type: it is not checked for overflow
- There are no compound forms (`&=`, `<<=`). Compile-time expressions evaluate all of them, by arithmetic (`comptime_bit_op` in `ir_gen_comptime.dm`): the compiler's own source may not use an operator that the seed's compiler does not have

### Lines
- A newline ends a statement. An expression goes on over a newline where the line ends in an operator, or the next line begins with one that cannot begin an expression: `+`, `/`, `%`, a comparison, `and`, `or`, `^`, `<<`, `>>`, `|>`, `.name` and `as`
- A line that begins with `-`, `*`, `&`, `|` or `[` begins a new expression (`starts_expression` in `parser.dm`): `*b = 5` after `let y = 2` is a statement of its own. Until 2026-11-22 it was parsed as `2 * b = 5`, a syntax error

### List Methods
- `let mut l: List[T] = []` — empty list (type annotation required)
- `l.push(item)` — append
- `l.pop()` — remove and return last
- `l.len()` — get length as int
- `l[i]` — index access
- `for item in list { ... }` — iterate

### Map Methods
- `let mut m: Map[K,V] = Map_new()` — empty map (type annotation required)
- `m.insert(key, value)` — insert or update
- `m.get(key)` — get value (panics if missing)
- `m.contains(key)` — check if key exists
- `m.remove(key)` — remove key
- `m.len()` — get number of entries
- `m.keys()` — get List[K] of all keys
- `m.values()` — get List[V] of all values
- `m.set(key, value)` — alias for insert
- `m[key]` — index access (alias for get)
- `m[key] = val` — index assignment (alias for insert)

`Map[K, V]` is the generic struct in `stage5/runtime/map.dm`. Keys must be strings or integers, `keys()`/`values()` and `for k in m` follow insertion order, and `Map_new()` needs a destination type (a typed `let`, a struct field, an assignment target or a return). Copying a map copies its list headers, so the copy shares storage with the original, as lists do. There is also the builtin `byte_at(s, i) -> int` (the byte at index `i`, bounds-checked).

### Runtime Primitives

These are the low-level features the runtime is written with. The builtins below need an `unsafe` block. Addresses are `int`s.

| Builtin | Description |
|---------|-------------|
| `load_T(addr)` | Read a `T` at `addr`, where `T` is `u8`, `i8`, `u16`, `i16`, `u32`, `i32`, `i64`, `f32` or `f64`. Integers widen to `int` (zero- or sign-extended), floats to `float` |
| `store_T(addr, v)` | Write `v` at `addr` as a `T` (narrowing it) |
| `addr_of(place)` | Address of a variable, field or list element |
| `size_of[T]()` | Size of type `T` in bytes |
| `string_data(s)` | Address of a string's bytes. A NUL byte follows them, except in a string that `string_from_raw` made from memory without one |
| `string_from_raw(ptr, len, cap)` | The string at `ptr`; `cap` 0 means the string does not own the memory |
| `symbol_addr("name")` | Address of the data symbol `name`, such as the C library's `stdout`. The name is a string literal; naming a function is a compile error |
| `static_addr("name", size)` | Address of `size` bytes of the program's own storage, zeros when the program starts. Both arguments are literals. One name is one block of storage wherever it is used; two sizes for one name is a compile error |

- **C-width integers**: integers of different types in one expression meet at one type. A literal takes the other operand's type (`fd < 0` with `fd: i32`), otherwise the narrower operand widens. `u8`/`u16`/`u32`/`u64` compare, divide and take remainders unsigned. An integer that goes to a place of another integer type becomes that type: a constant that fits and a narrower value convert, and a wider value is a compile error that asks for `as`. The places are a `return`, an assignment, a typed `let`, an argument of a function or a method called by name, a lambda called by its name or a function value, a struct literal's field, a variant's value, `Some(x)`, `Ok(x)`, `Err(x)`, `Box_new(x)`, a list literal's element, `xs.push(x)` and the place of a compound assignment (`convert_int_value`, `convert_int_to_place` and `convert_list_elem` in `ir_gen_expr.dm`). A literal that doesn't fit its type is an error. An `if` or a `match` whose branches all give constants takes the type of its place as a literal does (`branches_give_int_literals`): `let c: i32 = if ok { 0 } else { 1 }`. The value's type is found in IR generation, where it is `i64` when nothing is known, as for the value of a `?`; so the narrowing error is given only where the checker's type for the value, when it has one, does not fit either. Until 2026-11-21 only a `return` and an assignment were checked: `let a: i8 = big`, `take(mid)`, `S { n: mid }` and `ys.push(big)` kept the low bits without a word. The branches of an `if` and the arms of a `match` meet the same way (`int_meet_type` in `ir_gen.dm`, which the checker and IR generation both use): `match o { Some(x) => x, None => 0 }` with `o: Option[i32]` is an `i32`, `if c { x } else { big }` with `big: int` is an `int`, and a literal that does not fit the other branches' type is an error. Each branch's value is converted to that type where it is stored (`store_branch_value` in `ir_gen_expr.dm`), and an `f32` and a `float` are converted to the first branch's type. Until 2026-11-21 the value had the first branch's type, or `int` for a match on an `Option` or a `Result`, and the other branches were stored as they were: a narrow value left the upper half of a wide slot unset (`-7` read as 4295177289, or as garbage), a wide value overran a narrow slot, and an arm that was a block ending in a narrow value gave none.
- **Compound assignment**: `place op= value` with `+=`, `-=`, `*=`, `/=` and `%=` is `place = place op value` with the place found once: the same overflow and zero-divisor checks, strings concatenated, a struct's `add`, `sub`, `mul` or `div` method called (`generate_compound_value` in `ir_gen_stmt.dm`, over `emit_binary_op`, the one function that emits a binary operator on two values). The place is a variable, a field, a list element (also of a list in a field or a box) or a map entry. Until 2026-11-22 `xs[i] += v` stored `v`, `s += "b"` and `p.name += "y"` failed LLVM verification, `d /= 0` was not checked, and `%=` did not exist. An overloaded operator's left operand may be any expression of the struct's type, so `a + b + c`, `p.lo + p.hi` and `mk(1) + mk(2)` call the method; before, only a variable did.
- **`for x in xs`** visits the elements the list had when the loop began, and ends early when the body has shortened the list: each round tests the index against the first length and against the length now. Elements the body pushes are not visited. Before 2026-11-22 a body that popped an element made the loop read past the end and panic.
- **Narrow C arguments**: a call of a source `extern fn` marks its `i8` and `i16` arguments `signext` and its `u8`, `u16` and `bool` arguments `zeroext` (`mark_narrow_c_args` in `llvm_gen_call.dm`), as the x86-64 C calling convention has the caller widen them to 32 bits. Without the mark `abs` of an `i8` -5 gave 251.
- **Variadic externs**: `extern fn printf(fmt: string, ...) -> i32`. The C function is called directly: string arguments pass as `char*`, and extra arguments get C's default promotions (`f32` to double; `bool`, `i8` and `i16` to `i32`). A variadic extern can't return `string`.
- A source `extern fn` may declare a C function the compiler also uses, such as `extern fn malloc(n: int) -> int`; each call uses its own declaration's types.
- **Link names**: `extern fn my_len(s: string) -> u64 = "strlen"` binds the extern to the C symbol `strlen`. Several externs may name one C symbol; each call uses its own declaration's types.
- **Functions named like C symbols**: a dAImond function whose name is a C symbol the module declares, such as a program's own `fn rename` or `fn strlen`, gets the symbol `<name>.dm` (`dm_symbol_of` in `llvm_gen.dm`), so the runtime's calls of the C function still reach C. The compiler's own calls of libc (`malloc` for `Box_new`, `exit`) go through externs named `dm_libc_<symbol>`, which a program can't shadow.

### The Runtime

The runtime of every program is dAImond code in `stage5/runtime/*.dm`, which `gen_bootstrap.dm` embeds in the compiler (`prelude.dm`) and the compiler adds to every program.

- The IR names a runtime function `dm_X`, and the dAImond function `rt_X` is what runs: the compiler binds every call to `dm_X` to `rt_X` (see RUNTIME FUNCTIONS in `llvm_gen.dm`). `rt_X` must keep the signature `dm_X` is declared with in `ir_gen_decl.dm`, except that it takes an `int`, the address, where `dm_X` takes a pointer; a mismatch is a compile error.
- To add a runtime function: declare `dm_X` in `ir_gen_decl.dm`, write `rt_X` in a runtime file, and run `gen_bootstrap.dm`. A new runtime file also needs a line in `gen_bootstrap.dm`. A `dm_X` with no `rt_X` fails to link.
- The runtime's functions: `string_concat`, `string_eq`, `string_cmp`, `char_at`, `substr`, `string_contains`, `string_find`, `starts_with`, `ends_with`, `string_trim`, `string_replace`, `string_to_upper`, `string_to_lower`, `string_split`, `is_alpha`, `is_digit`, `is_whitespace`, `is_alnum`, `char_to_string` (`runtime/string.dm`); `int_to_string`, `uint_to_string` (what `print`, an f-string and `int_to_string` make of a `u64`), `float_to_string`, `bool_to_string`, `parse_int`, `parse_float` (`runtime/convert.dm`); the list operations push, pop and contains for int, float, string and other elements, and the element read `for x in xs` makes (`runtime/list.dm`); `file_read`, `file_write`, `file_append`, `file_exists`, `fs_mkdir`, `fs_readdir`, `fs_remove`, `fs_rename`, `fs_getcwd`, `env_get`, `args_len`, `args_get`, `system`, `run_command` (`runtime/os.dm`); `path_dirname`, `path_basename`, `path_extension`, `path_stem`, `path_join` (`runtime/path.dm`); `print`, `println`, `eprint`, `eprintln`, `flush`, `read_line`, `read_key`, `read_key_nb`, `term_width`, `term_height`, `panic` (`runtime/io.dm`); `time_ms`, `sleep_ms` (`runtime/os.dm`); `chr` (`runtime/convert.dm`); `mem_mark`, `mem_sweep` (`runtime/string.dm`); `tcp_listen`, `tcp_accept`, `tcp_connect`, `tcp_read`, `tcp_write`, `tcp_close` (`runtime/net.dm`); `thread_spawn`, `thread_join`, `mutex_new`, `mutex_lock`, `mutex_unlock`, `mutex_destroy` (`runtime/thread.dm`). Floats go through libc's `snprintf("%g")` and `strtod`; integers are formatted and parsed in dAImond.
- A list is `{ data, len, capacity }` and is passed to the runtime as the address of that header.
- Inline, with no function behind them: `len(s)`, string literals, `xs.len()`, the creation of an empty list, `xs[i]` and `xs[i] = v` (one bounds check, then a load or store at the element's address), and the overflow and range checks on signed arithmetic and narrowing casts (`dm_checked_*`, `dm_cast_check_*`), which lower to LLVM's overflow intrinsics and a branch to a panic block.
- **Console**: output and `read_line` go through libc's `stdout`, `stderr` and `stdin` streams, reached with `symbol_addr`, so they keep their order with C code that uses the same streams. `read_line` gives a whole line however long it is.
- **Program start**: `main` begins with a call of `dm_start` (`rt_start` in `runtime/os.dm`), which raises the limit on the stack's size to 64 MB where it is lower, or to the highest value allowed when that is below 64 MB. A C constructor did this before `main`. The stack of a running program grows up to the limit in force, so the raise takes effect at once.
- **Linking**: the compiler starts `ld.lld -pie` itself, with `run_command` and no shell, on the program's object, the precompiled runtime object at `-O0`, the C library's start-up objects (`Scrt1.o`, `crti.o`, `crtn.o`) and `-lm -lpthread -lc` (see LINKING in `main_split.dm`). It takes `ld.lld` from `$DAIMOND_LD`, else `PATH`, else the newest `/usr/lib/llvm-<version>/bin`; and the C library's directory from `$DAIMOND_LIBC_DIR`, else `/usr/lib/x86_64-linux-gnu`, `/usr/lib64` or `/usr/lib`. The dynamic loader is glibc's on x86-64 Linux, `/lib64/ld-linux-x86-64.so.2`. With `--link-llvm` it adds the LLVM library: `$DAIMOND_LLVM_LIB`, else `libLLVM.so` in `lib/` or `lib64/` next to the `bin/` that holds the linker once its symbolic links are followed (`find_llvm_library`; `/usr/lib/llvm-19/lib` on Debian, `/usr/lib` on Arch). `bootstrap.sh` finds it the same way. Until 2026-11-22 the link line went through `/bin/sh` and asked `llvm-config` for the library; neither is needed now.
- **Running programs**: `run_command` and `run_command_io` start a program with libc's `posix_spawnp` and wait for it (`rt_run_command` in `runtime/os.dm`). Each argument reaches the program as it is: nothing is split, expanded or quoted, because no shell takes part. Like `system`, the caller ignores SIGINT and SIGQUIT while it waits, and what it has written to its streams is flushed first. The sizes of glibc's `posix_spawn_file_actions_t`, `posix_spawnattr_t` and `sigset_t` on x86-64 Linux are assumed (each gets more room than it needs).
- **Terminal and time**: `chr`, `flush`, `read_key`, `read_key_nb`, `term_width`, `term_height`, `time_ms` and `sleep_ms` are builtins, which `examples/snake.dm` and `examples/breakout` use. `read_key` and `read_key_nb` read libc's `stdin` stream, so they see what `read_line` left in its buffer. `read_key_nb` asks `poll` about file descriptor 0: bytes already in the stream's buffer are not seen until the descriptor has more. `sleep_ms` with a negative time does not wait. `mem_mark()` is 0 and `mem_sweep` does nothing.
- **OS constants**: `TIOCGWINSZ` (21523), `CLOCK_MONOTONIC` (1), `POLLIN` (1) and the layouts of `struct winsize`, `struct pollfd` and `struct timespec` are those of x86-64 Linux.
- **Assertions**: `assert(cond)` panics with `assertion failed`. `assert_eq(a, b)` compares with `==`, so it takes whatever `==` does, and panics with `assert_eq failed: strings not equal` or `assert_eq failed: values not equal` (`rt_assert*` in `runtime/io.dm`). A call the IR generator emits of a function that was never declared is a compile error (`internal: call of ...`); it used to be dropped, which is how both assertions did nothing.
- **Enums and `match`**: an enum is a struct of its tag and then one field for each value of each variant (`Variant_0`, `Variant_1`, ...; `enum_payload_field` in `ir_gen.dm`), so a variant carries any number of values of any types. A pattern binds each value as a variable of its type (`track_bound_variable` records the type, as for a parameter), and so do `Ok`, `Err` and `Some`; a pattern may bind fewer values than the variant carries. An arm that is a name binds the matched value with its type. A string is matched against string literals by its text. The matched value's type comes from the expression (`static_type`), so a call can be matched directly. A wrong number of values, in a constructor or a pattern, and a variant the enum does not have are compile errors. The arms are tried in the order they are written (`generate_variant_match` in `ir_gen_expr.dm`): the arm of a variant is taken when the value is that variant and the arm's guard, if it has one, holds, and a name or `_` takes any value. A guard may read what its pattern binds (`Color.Blue(n) if n > 5 =>`, `Some(v) if v > 0 =>`); an arm with a guard does not count toward the match having an arm for every variant. An `Option` and a `Result` are matched by the same code, as the enums they are laid out as. A value of a variant's pattern is a name, `_` or a literal: an integer, a string or a bool (`Token.Number(0) =>`, `Some("x") =>`, `Err(_) =>`). The parser gives a literal a name of its own (`$lit_LINE_COL`) and adds `name == literal` to the arm's guard (`parse_variant_value` in `parser.dm`), so an arm with a literal does not count toward covering its variant either; anything else there is a syntax error (it was taken as a name). A pattern may be a negative integer (`-1 =>`). Until 2026-11-22 a guard on a variant's arm was a compile error, a guard on a `_` arm of a match on an enum was ignored, and a match on an `Option` or a `Result` took the last arm of each variant, and its `_` arm only for `None` or `Err`: `match o { None => 0, _ => 1 }` gave no value for a `Some`.
- **Generic enums** (GENERIC ENUMS in `ir_gen_expr.dm`): `enum Opt[T] { Has(T), Empty }` is one enum for each set of type arguments it is used with, as a generic struct is one struct: `Opt[int]` is the enum `Opt_i64`, registered when a type names it (`ensure_type_instances`, `register_enum_instance` in `ir_gen_decl.dm`). A constructor names no type arguments. The checker finds them from the values (`Opt.Has(3)` is an `Opt[int]`; `ck_enum_value_type`) and, for what the values do not say, from the place the value goes to (`let e: Opt[int] = Opt.Empty`, an argument, a `return`; `ck_settle_variant`); IR generation reads them at the constructor's id (`generic_enum_type`), and in the body of a generic function, where the checker records nothing, takes them from the values' types and then from the function's return type. A constructor whose type arguments nothing says is a compile error. A match on a generic enum is on the instance that is the matched value's type. Methods (`impl Opt[T]`), generic functions over one (`fn or_else[T](o: Opt[T], d: T) -> T`), instances in fields, in lists and in each other, and recursive ones (`Node(Box[Tree[T]], Box[Tree[T]])`) work. A wrong number of type arguments, for a generic struct or enum, is a type error (`ck_type_arity`).
- **Scopes**: a variable lasts to the end of its block, and one declared while another of its name is in scope shadows it until then: a `let` in a block, a `for` variable, a lambda's parameter, a name that a match arm binds, and a second `let` of a name in one block (whose value may read the first). IR generation keeps a function's variables by name, in maps that know no scopes, so `unshadowed_declarations` (SHADOWED NAMES in `ast.dm`) first gives each variable that shadows another a name of its own, `x$1`, in a copy of the function; a function that shadows nothing is left as it is. The scopes are the checker's. `source_name` (`token.dm`) takes the `$1` off again, in error messages (`error_at`) and debug info. Until 2026-11-22 the inner variable took the outer one's place for the rest of the function: after `if c { let x = 99 }`, `x` was 99, and `match o { Some(x) => x, None => x }` read a slot that was never written.
- **List literals**: a literal of structs or enum values stores each whole (`push_whole_value`), with or without a type annotation on the variable, and a literal can be passed straight to a function.
- **List values**: a list's value is the address of its header, `{ data, len, capacity }`: a variable's storage, or the storage a literal made (an alloca of the IR type `list`). LLVM generation records such an address (`string_ptrs`) and a store of it copies the header, so a list that is assigned, held in a field, pushed onto a `List[List[T]]` or assigned to an element of one is stored whole; the copy shares the elements' storage with the original. A call's result is the header itself. A literal whose elements are lists (`[[1, 2], [3]]`, `[xs, ys]`, `[mk(), mk()]`) takes its element type from `static_type` (`nested_list_elem_type` in `ir_gen_expr.dm`), and `let xs: List[T] = <value>` stores any value that is not a literal, `List_new()` or `List.new()`. Until 2026-11-21 a literal's address was stored as a pointer, and a typed `let` dropped a value that was not a literal: `let xs: List[int] = f()` gave an empty list, and `xs = [1, 2]` and `r.cells = [1, 2]` changed nothing.
- **Debug info** (`-g`; DEBUG INFO in `llvm_gen.dm`): the program carries DWARF, written through LLVM's DIBuilder (`dm_llvm_di_*` in both bridges): its files, each function with its file and line, the line of each instruction, and each parameter, `let` variable and `for` variable with its type. gdb and lldb can then set breakpoints by file and line or by function, step, show a backtrace and print variables (`print p.x`, `print name.data` for a string's text, `print *xs.data@xs.len` for a list's elements, `print *node.next` through a box). IR generation marks each variable with an `OP_DEBUG_VAR` instruction, only when `-g` is given (`debug_var` in `ir_gen_stmt.dm`); LLVM generation turns the marker into a declaration of the variable's storage, and makes the type by its name (`di_make_type`: numbers, `string` and `List[T]` as `{ data, len, capacity }`, `Box[T]` as a pointer, a struct with its fields, any other type as bytes of its size). A function has debug info when it is declared in a file: the runtime's functions have none, so a debugger steps over them. The stores of a function's parameters have no line, which makes them its prologue, so a breakpoint on the function stops after them. `-g` sets the module's data layout before code is generated, where sizes and offsets come from. `tests/cases/84_debug_info/dwarf.sh` prints a program's debug info in short, with `llvm-dwarfdump`. The compiler builds itself with `-g` (about 1.2 times the time; a 58 MB binary), and gdb debugs it by `main.dm`'s lines.
- **Lines in files**: a line number says which file it is in. Line L of file number F is `F * FILE_LINE_SPAN() + L` (`token.dm`); the file being compiled is number 0, each imported file takes the next number as it is loaded, then the LLVM bridge (`--link-llvm`) and the runtime (`<runtime>`). The lexer numbers lines this way (`tokenize_file`), so every token, AST node and IR instruction carries its file. The names are in `SourceFile.files`, then `IRModule.files`. Print a line with `line_in_file`, and build an error with `error_at` (IR generation) or `lg_error` (LLVM generation): an error in another file than the one being compiled begins with `FILE: `, as in `geometry.dm: Error: undefined variable 'x' at line 6`. The language server shows such an error where the file is imported.
- **Imports**: a file is loaded once however many files import it (`Imports` in `main_split.dm`). Until 2026-11-20 the set of loaded files was a `Map` passed by value, whose inserts the caller never saw, so a file imported by two files was compiled once for each: the language server's ten modules took 7.5 s and 2.2 GB to compile, and take 0.9 s and 174 MB now. A function, type or constant declared more than once is an error (`duplicate_declarations`; an `extern fn` may be repeated), and so is a function or an `extern fn` with the name of a builtin, which a call by that name could never reach (a user's `fn exit` was silently never called), and so is an import whose file does not exist (it printed an error and built the program anyway).
- **Language server** (`lsp/`, a dAImond program of its own, not part of the compiler): it reads no dAImond itself. It starts the compiler directly (`run_command_io`), with no shell. For a document's errors it runs `daimond check <path> --stdin` with the editor's text on standard input and places each line of the output (`add_error_line` in `documents.dm`); for its declarations it runs `daimond symbols`, for the document and, by their time of change, for the files it imports. What is inside a function it reads from the text by its shape: `let name`, `for name in`, parameters, names bound by a match arm (`declaration_kind` in `lookup.dm`). References are found by name, in code only (not in strings or comments); a variable's are those in its function. Hover shows the comment lines above a declaration. A string is never freed in dAImond, so the server makes none while it serves: it works in reused buffers and views of them (`buffer.dm`), and its memory stays flat (77 MB after 5 rounds of every request and after 150). Changed documents are checked once the editor has been quiet for `--debounce` milliseconds (200; 0 checks after every change, which the suite uses for a fixed order of messages). Its cases are `tests/cases/83_language_server/`: each is a directory with the documents and a `messages` script, played by `session.sh` through `lsp/test_client.dm`.
- **For editors**: `symbols` prints one line per declaration, tab-separated: kind (`import`, `function`, `struct`, `field`, `enum`, `variant`, `trait`, `impl`, `method`, `const`), name, line and column of the name (from 1), last line, the type a field, variant or method belongs to, and the declaration's first line such as `fn add(a: int, b: int) -> int` (the file, for an import). It prints what could be read of a file with syntax errors. `check` accepts a file without `main`. `--stdin` reads the program from standard input.
- **Commands** (COMMANDS in `main_split.dm`): `run` builds into `/tmp` (or the file `-o` names, which it keeps) and gives the program's exit code. The program is started with `run_command`, so the arguments after `--` reach it as they are; so are the linker and each test of `daimond test`. The compiler runs no shell. `check` runs the pipeline through LLVM verification and builds nothing. `fmt` re-indents by braces. `test` replaces the file's `main` with a generated one that runs the program once per `test_*` function, so a panic ends only that test; it prints `test NAME ... PASS` or `FAIL: <panic message>`, then `N passed, M failed`, and exits with 1 when a test fails.
- **Panics**: `dm_panic` (`rt_panic` in `runtime/io.dm`) writes `PANIC: <message>` to stderr and exits with code 1. Messages passed to it, by the compiler's checks or by runtime code, do not include the prefix.
- **Sockets** (`runtime/net.dm`): IPv4 over libc's sockets, with no name lookup. An address is `HOST:PORT`, where `HOST` is a dotted address, `localhost`, or nothing (`0.0.0.0`). `tcp_listen` and `tcp_connect` give -1 when they fail, which includes a host that is not an address and a port above 65535.
- **Threads** (`runtime/thread.dm`): `thread_spawn(f)` takes a function that takes no arguments, by its name or as a `fn()` variable; anything else is a compile error. The function itself is the pthread start routine, which relies on the x86-64 calling convention (see the comment on `rt_thread_spawn`). It panics when the thread cannot be started. A mutex is the address of a `pthread_mutex_t`. Nothing in the language shares data between threads safely; `static_addr` storage and a mutex is the way the tests do it.
- **Functions as values**: a function's name is a value (its address) wherever the function is declared, also further down the file. A lambda in a variable without a type annotation (`let f = |x: int| -> int x + 1`) can be passed where a `fn(int) -> int` is expected; a lambda captures the variables of the enclosing function that its body names, as extra parameters, so one that captures any can only be bound with `let` and called by that name; using it as a value is a compile error.
- **Memory**: nothing is freed (see Not Yet Implemented), so a text must not be built by adding to it piece by piece in a loop: each `text = text + piece` copies the text so far, and n pieces of a text of length L cost about n × L / 2 bytes for good. Collect the pieces in a `List[string]` and call `join_strings(pieces)` (`lexer.dm`), which joins them in pairs and copies the text once per level of pairing. The lexer's `unescape_string` built each string literal a character at a time: the 60 KB literal that held the runtime's source took 1.6 GB of the 2.5 GB a self-build needed, and `daimond fmt` took 2 GB for a file of 20,000 lines. `gen_bootstrap.dm` also writes the runtime's source as literals of at most 4,000 bytes, so that a seed compiler from before the fix builds the compiler in 1.4 GB. `81_commands/long_sources_need_little_memory` holds both to 1 GB of address space.
- **Equality** (EQUALITY in `ir_gen_expr.dm`): `==` and `!=` compare numbers, bools and strings directly, a `Box` and a function by its address, and an enum whose variants carry no values by its tag. Two structs are equal when their fields are; two enum values when they are the same variant with equal values; two `Option`s or `Result`s likewise; two lists when they have the same length and equal elements. For each such type the compiler writes a function that compares two values, as source text (`eq_function_source`), and generates it the first time the type is compared (`made_function`; the function is named `eq$<type>`, which no source can write, and has no debug info); `a == b` is then a call of it, and the function's own `==` on the fields, values and elements reaches the functions of their types, so a type that contains itself (`struct Tree { kids: List[Tree] }`) is compared all the way down. A struct or an enum with a method `eq` is compared by that method wherever it stands (as a field, a list element, an `Option`'s value), and `!=` is `not eq` where the type has no `ne`. `xs.contains(v)` on a list whose elements are not integers, floats or strings looks for an element that `==` finds equal (`contains$<type>`). `assert_eq` compares with `==`. A `Map`, a `dyn` value and a SIMD vector are not compared: `==` on one, or on a type that holds one, is a compile error (`cannot compare Index with '==': it holds a Map[string, int]`), and so is `==` on two different types and `<`, `<=`, `>`, `>=` on values that are not numbers or strings and whose type has no method for the operator. In a generic function `a == b` compares what the type argument is. A struct without fields is a type of size zero (it had no body in LLVM, and did not compile). Until 2026-11-22 `==` compared two enum values by their variants only (`Shape.Rect(1, 2) == Shape.Rect(1, 3)` was true), failed LLVM verification on structs, `Option`s, `Result`s and lists, compared two lists by the addresses of their headers (a list was equal only to itself), and `contains` on a list of structs did not compile.
- **Instances** (INSTANCES in `check.dm`): `check_program` checks the body of a generic function, and of a method of a generic struct or enum, with the type parameters standing for any type (`?`), and records no types for its expressions. Code generation makes one copy of the function for each set of type arguments, and before it generates a copy it has the checker check the function again with the type parameters standing for those arguments (`instance_types_begin`, called where `generate_generic_call`, `ensure_instance_method` and the generic methods of a struct generate an instance; the checker is kept in `IRGenerator.checker`). So inside an instance a `match`, an `if`, a `None` and a list literal have the types the arguments give them, and a mismatch that depends on the type arguments is an error that names the instance: `operator '+' does not take Point and Point at line 14 (in total[Point])`. The types are recorded at the same expression ids for every instance (`FunctionDecl.expr_from` and `expr_to` are the function's ids), so the ones that were there are kept and put back when the instance is generated (`instance_types_end`): an instance can be generated in the middle of another. A type argument that code generation only guessed (it takes type argument i from argument i where the checker found none) or has in a form the checker does not know stands for any type. Until 2026-11-22 nothing was recorded there, and `return match o { Some(v) => v, None => fallback }` with `T = string` read a string from an 8-byte slot.
- **Trait bounds**: `fn show_all[T: Show + Named](xs: List[T])` (`FunctionDecl.generic_bounds`, `FnSig.bounds`): the type a call gives for `T` must have an `impl` of each trait, or the call is an error (`'shown' takes for T a type that implements Show, which Plain does not`, `ck_apply`); a trait that does not exist is an error where the function is declared. Inside the function a method call on a `T` is checked for each instance. Only a function's own type parameters take bounds, not those of a struct, an enum or an impl.
- **Compile-time evaluation** (`ir_gen_comptime.dm`): the value of a `comptime` expression and of a `const` is found by an evaluator that walks the AST with variables of its own (`CtState`; a function that is called sees only its own). It takes integers, floats, bools, strings and lists; every operator, with `and` and `or` leaving the right side alone where the left decides; `if`, `match` on literals and names with guards, blocks; `let`, assignment and compound assignment to a variable or a list element, `xs.push(v)`, `while`, `loop`, `for` over a range or a list, `break`, `continue`, `return`; calls of the program's functions, to any depth of recursion up to 200, and of `len`, `int_to_string`, `float_to_string`, `bool_to_string`, `char_at`, `substr`, `string_contains`, `string_find`, `starts_with`, `ends_with`, `string_trim`, `string_to_upper`, `string_to_lower` and `string_replace`; f-strings; casts between numbers; a constant that is declared further down. Its result must be a number, a bool or a string. Everything else is a compile error that says what was not evaluated (`a field ('.x') cannot be evaluated in a compile-time expression at line 12`), and so is what would be a panic in the program (integer overflow, division by zero, an index out of range, a cast that does not fit), a name that is not a constant or a variable of the expression, and a computation of more than a million steps (loop turns and calls). Until 2026-11-22 whatever the evaluator did not take had the value 0, a loop stopped after 10,000 turns without a word, a called function could read its caller's variables, and an overflow was a panic of the compiler.
- **Unsigned integers as text**: `print`, an f-string and `int_to_string` take an integer of any type and print the number it is, and so does any builtin that takes an `int`: the value widens to 64 bits by the sign of its own type (`emit_int_to_string` and `generate_builtin_call` in `ir_gen_builtins.dm`), and a `u64` goes to `rt_uint_to_string`. Until 2026-11-22 a narrow value was sign-extended whatever its type: `println(u)` with `u: u8 = 200` printed `-56`.
- **f-strings**: each value in `f"..."` is printed as the type of its expression (`infer_part_type` is `infer_expr_type`), and a value that is no string, number or bool is a type error. Until 2026-11-22 only a variable's type was looked up, and any other expression was printed as an int: `f"{p.name}"` printed an address. The text of an f-string takes the escapes a string does (`\n`, `\t`, `\"`, `\\`), and `{{` and `}}` are braces of the text. A string inside an expression is written with `\"` (a plain `"` ends the f-string): `f"{m.get(\"k\")}"`. A `{` without a `}`, an empty `{}` and a string without an end in an expression are syntax errors (`parse_fstring`). Until 2026-11-22 an escape in an f-string was printed as it was written, backslash and all.
- **Constants**: the value of a `const` is found by the compile-time evaluator, with `comptime` or without it (`generate_constant` in `ir_gen_decl.dm`), so it takes every operator and calls of functions. A division or a remainder by zero there is a compile error, as a shift out of range is. Until 2026-11-22 a constant without `comptime` had an evaluator of its own that knew `+`, `-`, `*` and `/`: `const A = 17 % 5` was 0.
- **Float literals** may have an exponent: `6.02e23`, `1.5e-3`, `2E+3`.
- **Module names** may be dotted: `module tests.arithmetic`.
- **Deep expressions**: a chain such as `a + b + c + ...` nests one level per operator. `generate_binary` and `infer_expr_type` walk such a chain in a loop, and 400 terms compile. Other nesting still recurses, at 0.2 to 1.7 MB of stack per level in an `-O0` build of the compiler (each `IRGenerator` returned by value gets its own stack slot), so an expression nested several hundred levels deep, or a chain of about 1,000 terms, overflows the compiler's 64 MB stack and it crashes.
- **Command-line arguments**: `main` stores its argument count and vector in the symbols `dm_argc` (a C `int`) and `dm_argv`, which the compiler defines in the module that has `main`. The runtime reads them through `symbol_addr`. `args_get(i)` gives a string that points at the argument's own bytes.
- **OS struct layouts**: `fs_readdir` reads the name in libc's `struct dirent` at byte 19 (`rt_dirent_name_offset` in `runtime/os.dm`), which is its place on x86-64 Linux. Another target needs its own offset.
- **Bitcode**: `--emit-bitcode` writes `<output>.bc`, the module as it goes to code generation: with the host's target triple and data layout, optimized as the `-O` level says, and with the runtime compiled in. `llc -filetype=obj -relocation-model=pic` turns it into the object the compiler would have written.
- **Precompiled runtime object**: a `-O0` build does not compile the runtime's non-generic functions into the program. It links `runtime-<build ID>.o`, which the compiler builds once with full optimization and keeps in `$DAIMOND_CACHE_DIR`, else `$XDG_CACHE_HOME/daimond`, else `~/.cache/daimond` (see PRECOMPILED RUNTIME in `main_split.dm`). When the object can't be built or stored, the runtime is compiled into the program instead. `--emit-llvm`, `--emit-bitcode`, `--emit-ir` and `-O1` and above always compile it into the program, where the optimizer can inline it.
- The build ID is a hash (two polynomial hashes, as 16 hex digits) of the compiler's source, the runtime sources and `llvm_bridge.dm`, written into `prelude.dm` by `gen_bootstrap.dm`. Rerun `gen_bootstrap.dm` after changing any of them, the bridge included, or the compiler keeps linking the old object.
- Generic runtime code (the methods of `Map`) is always compiled into the program. At `-O0` the program's own functions are marked `optnone` and stay as written, while that generic code is optimized.
- `parse_int` and `parse_float` read the whole string.
- Runtime code calls libc through link-named externs (`libc_malloc`, `libc_memcpy`, `libc_memcmp`, `libc_memmem`, `libc_fopen`, ...), so a program's own `extern fn malloc` cannot collide with it. It must not use the operators it implements (no `+`, `==` or `<` on strings in `string.dm`).
- Every string the runtime builds is followed by a NUL byte, as every literal is, so its data can go to C as a `char*`. The file functions and `system` pass paths and commands this way, without a copy.
- A search pattern longer than the string is not found: `string_split("ab", "abc")` is `["ab"]` and `string_replace("", "a", "b")` is `""`. `string_split(s, "")` gives the bytes of `s`, and `is_alpha("_")` is false.
- Files go through libc's stdio. `file_read` reads a file that reports no size piece by piece to its end, so it reads pipes and files in `/proc`.
- `substr` with a negative start or length returns `""`.

## History

The language was first implemented by a compiler written in Zig that emitted C ("Stage 0"), then by a C-emitting compiler in dAImond ("Stage 1"), an LLVM backend in Zig ("Stage 3") and one in dAImond ("Stage 4"). The compiler in `stage5/` began as Stage 4 plus memory-safety checks. The others, the C runtime (`daimond_runtime.c`, `llvm_wrappers.c`) and the C bridge to LLVM (`llvm_bridge.c`) were deleted once this compiler built itself from the seed and had their tools. They are in the repository's history up to commit `2ddc25f`. `docs/stage-history.md` describes them and lists where this compiler behaves differently from Stage 0. Comments in the source that say "Stage 0" mean that compiler.

## Compiler Architecture

The compiler produces native binaries by calling LLVM's C API through the LLVM bridge.

### Design Decisions
- **Pipeline**: Lexer → Parser → AST → dAImond IR (SSA) → LLVM IR → native binary.
- **Integer kind tags**: `fn EXPR_FUNCTION_CALL() -> int { return 40 }` constants; a node is one struct with the fields of every kind.
- **Type checker** (`check.dm`): `check_program` runs before IR generation, on the program with its imports and the runtime, and the compilation stops when it reports anything (`Error: N type errors`). It finds the type of every expression as a string in source form (`List[string]`, `fn(int) -> bool`); `""` is a type it does not know and `?` stands for any type (`Option[?]` is `None`), and it reports a mismatch only when both sides are known. Every integer type fits every other (IR generation checks narrowing) and so do `f32` and `float`; an `int` given where a `float` is expected is an error. Two function types must take the same parameters and return the same type, widths included (`ty_fn_agrees`); a function's name is a value of its type. Array and `dyn` types are not compared, except that a struct given as a `dyn Trait` must implement the trait. Inside a generic function its type parameters are `?`; a call binds them from its arguments (`ty_bind`). A `match` on an enum, an `Option`, a `Result` or a `bool` must have an arm for every variant or a `_` arm, and so must any `match` whose value is used. A function that returns a value must end in a `return`, a `panic`, a `loop` or branches that all do (`ck_always_returns`); `main` is exempt. A value that is used must be given by every branch: an `if` needs its `else`, and a block must end in an expression, or leave with `return`, `break`, `continue` or `panic` (`ck_needs_value`). An `if` with an `else` and a `match` are such expressions where they end a block that is used as a value (`stmt_value_expr` in `ast.dm`: the parser keeps every `if` statement as an expression too), so `let v = { if c { 1 } else { 2 } }` needs no parentheses. A `match` that is a statement gives no value: its arms may be of different types, and code generation stores nothing for it (`match_slot_type` in `ir_gen_expr.dm`; until 2026-11-22 it stored each arm's value in a slot of the first arm's type, which overran the slot). Calls: an undefined function, a wrong number of arguments and the argument types of builtins (`ck_builtin_params`) are errors; `x.f(a)` where the type of `x` has no method `f` is the call `f(x, a)` of a function `f`, which IR generation is told (`checked_target`), and an error where there is none. What a call changes must be `mut`: the receiver of `push`, `pop` and of a `mut self` method, and an argument that goes to a `mut` parameter (`ck_changes`); what is reached through a `Box` may always be changed, since a `Box` is a pointer that its copies share. An async function is called under `await` and nowhere else, and `await` takes nothing but such a call (`ck_await`): the call runs the function to its end, so there is no value that stands for a call still running. Effects are checked here too (see Error Detection). The compiler's own source passes the checker; checking it adds under half a second and 70 MB to a self-build.
- **Checked types in IR generation** (CHECKED TYPES in `ir_gen.dm`): `check_program` gives, with the errors, the type of each expression at its id and the type arguments of each call of a generic function. Where a value goes says what the value alone does not: `None` is an `Option[?]` to the checker until `ck_settle` records the type of its place (`let o: Option[int] = None`, an argument, a field, a list element, a return value, the other branch of an `if`). IR generation reads them with `checked_type` (source form), `checked_ir_type` and `checked_type_args`: for `None`, `Some`, `Ok` and `Err`; for the type of the value of an `if`, a `match` or a block (`checked_slot_type`; found here from the first branch alone, it was wrong where a name the branch binds had been bound with another type before); for the type arguments and the result of a generic call (`first(ps)` is compiled for `T = P`, where it used to be compiled for the type of the first argument); and in `static_type` wherever the expression's parts do not say. Of numbers it takes one thing from the checker, which lets every integer type fit every other: the type the branches of an `if` or the arms of a `match` meet at (`checked_slot_type`), which the checker finds with the arms' own variables in scope, as IR generation cannot before it generates them. The checker types integer arithmetic and branches by `int_meet_type`, the rule IR generation converts by. In the body of a generic function it has the types of the instance it is generating (see Instances); for a `match` that is a statement, the branches' type is found from the branches (`arms_meet_type`). `infer_expr_type` and `static_type` still do the rest, and IR generation keeps its own checks (`check_basic_type`, argument counts, undefined functions).
- **What is in a box**: a method called on a box is called on what is in it, so `b.inc()` is `(*b).inc()` and a `mut self` method changes the value in the box (`generate_method_call` in `ir_gen_expr.dm`). A list, a map or a string in a box is indexed and has its methods called as itself (`unboxed_container`): `b.len()`, `b.push(x)`, `b[i]` and `b[i] = v`. Until 2026-11-21 a `mut self` method called on a box was given the address of the variable that holds the box: `bc.inc()` on a `Box[Counter]` changed the pointer, a method of a generic struct in a box crashed, `bm.insert(k, v)` on a map in a box hung, `b.len()` and `b[i]` on a list in a box were compile errors, and `b[i] = v` did nothing.
- **A struct's own methods**: `recv.method(...)` on a struct or an enum value, or a box of one, whose type has a method of that name calls it and has its declared type (`own_method_of` in `ir_gen_expr.dm`), before anything is decided by the method's name alone. Until 2026-11-21 a method named `get` was typed `int` and one named `contains` `bool`, as a map's and a list's are, and a method that two structs have under one name was typed, and on a receiver that is not a variable called, as the last struct's: `h.a.val()` called `B_val` with an `A`, which failed to compile.
- **Calls on a type**: `Type.name(args)` calls the function `name` of `impl Type` that takes no `self` (`static_call_target` in `ir_gen_expr.dm`); `Box.new(x)` and `Box.null()` are `Box_new(x)` and `Box_null()`. A variable in scope with the type's name is a value, and the call is a method call on it. `s.len()` on a string is `len(s)`.
- **LLVM bridge**: the compiler calls LLVM through 149 `dm_llvm_*` functions, which `llvm.dm` declares as `extern fn`. `llvm_bridge.dm` defines them in dAImond over LLVM's C API (`extern fn LLVMBuildAdd(...)`); `--link-llvm` adds that file to the program and each of its functions takes the place of the extern declaration of the same name (`add_llvm_bridge` in `main_split.dm`). The list of types or values LLVM takes as an array is built in `static_addr` storage (`dm_llvm_buf_*`); LLVM's enum numbers are written out in `llvm_bridge.dm`.
- **Modular source, one generated file**: the modules are separate `.dm` files; `gen_bootstrap.dm` concatenates them into `main.dm`, which is what `bootstrap.sh` and a self-build compile. Edit the modules, never `main.dm`.

```
runtime/io.dm      — Console: rt_print, rt_println, rt_eprint, rt_eprintln, rt_flush, rt_read_line, rt_read_key, rt_read_key_nb, rt_term_width, rt_term_height, rt_panic
runtime/net.dm     — TCP sockets: rt_tcp_listen, rt_tcp_accept, rt_tcp_connect, rt_tcp_read, rt_tcp_write, rt_tcp_close
runtime/thread.dm  — Threads and mutexes: rt_thread_spawn, rt_thread_join, rt_mutex_new, rt_mutex_lock, rt_mutex_unlock, rt_mutex_destroy
main_split.dm      — Entry point: the command line, imports, the commands, linking
main.dm            — Generated: the modules as one file (~26K lines)
```

### Error Detection
The compiler detects at compile time:
- **Unterminated strings**: Lexer detects EOF inside string literals and exits with error
- **Syntax errors**: the parser reports `Error at LINE:COL: expected ... but got ...`, the first error of each top-level declaration (what follows an error in a declaration is parsed out of step). An error in an imported file is prefixed with that file's path. The parser is passed by value, so its errors leave in `SourceFile.errors`; until 2026-11-20 they were read from the caller's copy, which was always empty, so no syntax error was ever printed. Loops that parse a list until a closing token skip a token they cannot use (`p_skip_stuck`), so no input makes the parser loop forever. Post-parse validation still catches parameters without types
- **Type errors**: the checker (`check.dm`) reports mismatched types, undefined variables and types, assignment to what is not `mut`, unknown fields and methods, missing returns and matches that leave a variant out, all of a program's at once, as `Error: ... at line N`
- **Undefined functions**: IR generation checks a `known_functions` map before generating calls
- **Effect violations**: the checker holds a function or method that declares effects (`with [...]`) to them: each builtin it calls needs its effect (`builtin_required_effect` in `ir_gen.dm`: `file_read` needs `FileSystem`), and each function or method it calls or names as a value needs the effects that one declares. A function that declares none is not held to any

### Bootstrap Chain
```
llc + ld.lld turn seed/daimond.bc into            → seed compiler
seed compiler compiles stage5/main.dm             → gen1
gen1 compiles stage5/main.dm                      → gen2 (same file as gen1 when the seed is current ✓)
gen2 compiles stage5/main.dm                      → gen3 (same file as gen2 ✓, when the seed is older)
the compiler compiles tests/harness.dm            → the harness, which runs tests/cases (565/565 cases pass)
```

## Important Notes

- `seed/daimond.bc` is a build product (3.4 MB of LLVM bitcode, written by LLVM 19). `bootstrap.sh --update-seed` writes it; each new version adds its size to the repository's history, so write it again only when the compiler needs a newer compiler to build it. A seed from the same source is byte-identical, so an unneeded update changes nothing.
- `bootstrap.sh` gives each generation its own runtime-object cache (`DAIMOND_CACHE_DIR`), so that the comparison of generations covers the runtime object too.
- `stage5/main.dm` (~26K lines) and `stage5/prelude.dm` are generated by `gen_bootstrap.dm`. Edit the modules and the `runtime/*.dm` files.
- The largest module is `ir_gen_expr.dm` (~8K lines). A function there returns its generator; see The Compiler's Source.
- A self-build takes about 135 seconds and 1.3 GB of memory at `-O0` (0.9 GB up to LLVM verification, which `check` shows in 9 seconds; the rest is LLVM writing the object). Until 2026-11-22 it took 2.5 GB, of which 1.6 GB was one string: see Memory below.
- The test harness and the compiler write files next to nothing they read: programs are built in `/tmp`. Do not run another compiler's output into the source tree either.
